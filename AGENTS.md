# filecoin-ffi agent guide

filecoin-ffi is the cgo bridge from Go to Filecoin's Rust stack: FVM execution through [ref-fvm](https://github.com/filecoin-project/ref-fvm), storage proofs through [rust-fil-proofs](https://github.com/filecoin-project/rust-fil-proofs), and BLS signatures. Lotus executes every message from network version 16 through it and links its proofs and BLS code, so its glue code and its `rust/Cargo.lock` are part of consensus.

## Where filecoin-ffi sits in Filecoin

- [Lotus](https://github.com/filecoin-project/lotus) vendors ffi as the `extern/filecoin-ffi` submodule with a `go.mod` `replace`; a change reaches Lotus only through a submodule bump. Lotus CI caches ffi's build outputs, so a new output must be added to its cache lists.
- [Curio](https://github.com/filecoin-project/curio) pins its own submodule, usually behind Lotus, builds from source with `cuda-supraseal` on Linux, and calls the sealing, SupraSeal and vanilla-proof APIs.
- Lotus and Curio call the `.install-filcrypto` and `clean` make targets by name, and each runs an `ffi-version-check` that reads `const Version int = N` from `version.go` by field position. Changing the value or the line's shape breaks both until they match; it is unrelated to `version.json`.
- ref-fvm's `AGENTS.md` describes the host contract ffi implements. [Forest](https://github.com/ChainSafe/forest) links the same fvm crates without ffi and must reach the same results.

An additive Go API needs only a consumer bump to be used; a changed signature, build output or release asset needs Lotus and Curio changes. Name them in the PR description. If a sibling checkout is available, read its `AGENTS.md` before changing a shared contract.

## Layers

- `filcrypto.h`, `libfilcrypto.a` and `cgo/libs_generated.go` are generated by `make` and gitignored; Go tooling fails with `undefined: filcryptoLibs` until `make` has run.
- A new proof type or exported function needs the Go wrapper, the `cgo/` binding and the Rust export. Keep existing C enum discriminants and go-state-types ABI values. Go's conversion switches return an error for unknown values; Rust's `From` impls stay exhaustive so the compiler catches a missing case.
- Cargo features, `install-filcrypto` switches and Go build tags move together: `FFI_DISABLE_FVM` selects the `*-no-fvm` features and pairs with the `nofvm` tag.

## Memory and the boundary

- Rust returns boxed results; Go defers `destroy()`, checks the error and copies outputs into Go memory first. To keep an owned value, nil it in the result before `destroy()`.
- Go passes borrowed pointers. Rust must not keep them past the call; CI runs the Go tests with `GOEXPERIMENT=cgocheck2`. A file passed by `Fd()` stays alive through the call (`runtime.KeepAlive`), and Rust borrows the descriptor without closing it.
- The blockstore callback allocates block data with `C.CBytes` and Rust adopts it with `Vec::from_raw_parts`. That holds only while Rust uses the system allocator, so a `#[global_allocator]` breaks it.
- The global handle registry holds each FVM's context and externs. The Go `FVM` wrapper owns the Rust executor, and its finalizer destroys the executor and unregisters the externs, so every method keeps `runtime.KeepAlive` on the receiver and the registry must not reference the wrapper.
- Proof and FVM exports catch panics and return them as errors. Go callbacks `recover()` and return an error code; Rust panics only on an unregistered handle or an unknown code.

## FVM glue

- `rust/src/fvm/engine.rs` maps network versions to fvm2, fvm3 and fvm4 (`EngineVersion::V1` is fvm2). A new network version extends that range and usually enables an `nvNN-dev` feature on fvm4, which must be dropped in the same change that takes the ref-fvm release removing it.
- ffi decides consensus inputs: the network-version mapping, the fvm features, and the machine config Lotus passes (chain ID, base fee and circulating supply as two 64-bit halves each, actor debugging, which actors can observe).
- The receipt's exit code, gas used and `events_root` are consensus, and Lotus rejects returned events whose root doesn't match. Traces and returned event bytes are informational: a trace that fails to build is returned empty, and a new ref-fvm trace event reaches Lotus only after ffi maps it.
- Each fvm major's kernel decides what a callback error means and what it charges: in fvm4 a randomness or consensus-fault error becomes an `IllegalArgument` the actor sees, a tipset CID error is fatal, and consensus-fault gas comes from the FVM's price list rather than Lotus's estimate. Trace a callback through the kernel of each major that uses it before changing its error or gas handling.

## Proofs and BLS

- Two paths verify proofs. Inside the FVM, ref-fvm calls the proofs crates in `Cargo.lock` directly for window PoSt, seal, aggregate and replica-update verification. The Go `Verify*` wrappers serve Lotus block validation (winning PoSt) and pre-FVM replay. Identify the caller before choosing what to change and how to test it; the Go proof lifecycle test covers the wrappers, not the syscalls.
- Sealing, proving and the vanilla-proof APIs are SP-only, but Curio depends on their exact signatures.
- BLS `HashVerify` returns false for empty input, mismatched counts or duplicate messages, and Lotus relies on that, short-circuiting the empty case itself. Changing the BLS crate or its domain separation tag is a consensus change.

## Dependencies and the lockfile

- `rust/Cargo.lock` is what Lotus ships: it links fvm2, fvm3 and fvm4 into one graph, where `wasmtime-*`, `cranelift-*`, `pulley-*`, `fvm_ipld_*`, `cid` and `multihash*` must resolve to one version each. An advisory fixed in ref-fvm stays live in Lotus until this lockfile moves; fix both.
- Bumps fall into three kinds. Consensus-sensitive families (fvm, wasmtime, proofs, BLS) follow the ref-fvm and rust-fil-proofs releases being integrated: hold the wasmtime family at their versions with `cargo update -p <crate> --precise <version>`, including leaf crates such as `cranelift-entity`. Crates whose types cross into the proofs and BLS crates (`group`, `ff`, `rand`) move from `blstrs` up through proofs before ffi. Independent crates, including advisory fixes, can move on their own. Dependabot's grouped cargo PRs need sorting the same way.
- A full update touches proofs and crypto code (blst, bellperson, neptune); read those diffs for accepted inputs and hot-path speed, beyond green tests.
- The release build uses `--locked`; a `Cargo.toml` change ships with its lockfile change. `build.sh` deletes `Cargo.lock` and runs `cargo update`; don't use it.
- Go dependencies follow Lotus's `go.mod`; ffi's is a floor for other importers.

## Building

- `make` runs `install-filcrypto` once, behind the `.install-filcrypto` stamp. The stamp depends only on the `rust/` directory, so editing Rust sources or changing `FFI_*` switches doesn't trigger a rebuild; use `make -B .install-filcrypto` or `make clean`. Both run `go clean -cache -testcache`, which clears the machine's Go build cache.
- On a HEAD with a release tag, `install-filcrypto` downloads the release asset and ignores the `FFI_*` feature switches unless `FFI_BUILD_FROM_SOURCE=1`. Otherwise, or if the download fails, it builds from source. `FFI_USE_GPU=0` skips CUDA and OpenCL; without `nvcc` on PATH a CUDA build falls back to OpenCL with a warning.
- Release assets are built with OpenCL and portable blst; PR CI builds from source, so CI doesn't test the binary Lotus downloads.
- Supported targets are Linux x86_64 and arm64 and macOS arm64.

### Testing unreleased ref-fvm

- Extend the existing `[patch.crates-io]` table in `rust/Cargo.toml`. It can patch all three majors under renamed keys (`fvm4 = { package = "fvm", path = ... }`, likewise `fvm3`, `fvm2` and each `*_shared`). Also patch `fvm_ipld_{encoding,blockstore,amt,hamt}` from the master tree, or the graph holds two copies of the blockstore and encoding traits. Don't commit the patch or its lockfile.
- Check that `cargo tree` resolves each patched crate to its local path, and that `cargo tree -i wasmtime -e normal --depth 1` still shows one wasmtime.
- Lotus links its own submodule (`go list -m -f '{{.Dir}}' github.com/filecoin-project/filecoin-ffi` in Lotus shows which). Rebuild there with `FFI_BUILD_FROM_SOURCE=1 make -B .install-filcrypto`, then run an itest or replay at a network version that selects the changed engine; a sync at the current network version doesn't exercise fvm2 or fvm3.

## Testing

- `go test` runs the proof lifecycle on 2 KiB sectors and needs parameters (`paramfetch 2048 parameters.json srs-inner-product.json`, with `FIL_PROOFS_PARAMETER_CACHE` set).
- ffi's tests don't execute the FVM; FVM glue changes need the Lotus run above.
- `CGO_ENABLED=0` CI builds don't exercise `nofvm`. For changes to build tags, FVM exports or feature wiring, also build with `FFI_DISABLE_FVM=1 FFI_BUILD_FROM_SOURCE=1 make -B .install-filcrypto` and run `go test -tags nofvm ./...`, then force a rebuild before FVM-enabled testing.
- CI doesn't run GPU proving, 32 or 64 GiB sectors, supraseal beyond a build, or tests on macOS beyond compiling them. `make cgo-leakdetect` (valgrind) runs only on manual dispatch. State what you ran and on what hardware.

### Commands

```sh
make             # build or download libfilcrypto, filcrypto.h, cgo/libs_generated.go
make clean       # clears the stamp, outputs and Rust target
GOEXPERIMENT=cgocheck2 go test -run TestProofsLifecycle .
(cd rust && cargo fmt --check && cargo test --locked --release --all)
(cd rust && cargo clippy --locked --all-targets --features blst-portable,opencl -- -D warnings)  # CI's clippy
make lint        # shellcheck and golangci-lint (new issues only)
```

## Releases

A PR titled `chore: X.Y.Z release` that bumps `version.json` creates a draft release and builds the assets; merging publishes it and tags (`RELEASE.md`). Add user-facing entries, including breaking changes, under `## Unreleased` in `CHANGELOG.md`.

## Change hygiene

Report suspected vulnerabilities privately as `SECURITY.md` describes, never in a public issue or PR.

### Comments, docs and commit messages

- Write code comments and reference docs year-zero: describe the code as it is, as if it had always been this way. Release notes may compare old and new behaviour. History (old behaviour, the bug, the fix, the issue) goes in the commit message and PR description. In comments, words like "now", "previously", "used to", "no longer", "instead of" and "fixed" signal change narration; rewrite or delete. A link that explains a constraint that still applies stays.
- A comment, in code or tests, earns its place by stating what a maintainer can't read from the code: intent, an invariant, a compatibility or consensus constraint, a surprising cost. Don't restate the code, the test name or the assertion; prefer one precise sentence. Public API docs state the contract: inputs, outputs, errors, bounds.
- Commit messages and PR descriptions explain what changed and why, for a reviewer. Skip summaries of the diff, boilerplate sections and claims you haven't verified.

### Pull requests

Use Conventional Commits form for PR titles, `<type>(<scope>): <description>`, with `!` before the colon for a change that breaks Lotus, Curio or the release assets.

## Reviewing changes

Read the Lotus and Curio callers, the ref-fvm or proofs code on the other side, and the tests before commenting, and verify assumptions against current code.

Priorities, in order: consensus inputs and dependency versions; memory safety across the boundary; Go API and build-output compatibility; build and release correctness; tests.

Comment only on a concrete, plausible failure the change introduces: the triggering input or state, the wrong result, its consequence. Skip style preferences, speculative hardening, pre-existing problems and refactors without behavioural benefit. One exception: this repository treats comments that narrate the change or restate the code as defects, so report them (see Comments, docs and commit messages).

## Maintaining agent context

This file is maintained with the code. When a change makes it wrong, fix it in the same PR. When a change alters a contract with a neighbouring repository, name the follow-up that repository needs, including its `AGENTS.md`, in the PR description.

Each `AGENTS.md` has a sibling `CLAUDE.md` containing only `@AGENTS.md`, because by default Claude Code skips `AGENTS.md` files whenever a `CLAUDE.md` exists at or above its working directory. Add the pair together; put content in `AGENTS.md`, never in the `CLAUDE.md`.
